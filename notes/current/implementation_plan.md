# Переписанный план: добавить смысл к готовой Библиотеке Вавилона

Статус: текущий рабочий план после аудита готового reader-а.

## Главная корректировка

Мы не строим Библиотеку Вавилона заново.

Готовый фундамент уже находится в этом проекте:

- `site/library.html` — готовый reader;
- `site/assets/library.js` — адресация, поиск, открытие, навигация;
- `experiments/backend_app.py` — raw `rank/unrank`, score и exact endpoints;
- `models/` — алфавит и конечные модели;
- `deploy/babel-walk.service` — production-сервис.

Reader уже поддерживает:

```text
4096 символов
256 знаков алфавита
0 … 2^32768 − 1
page64 и десятичный адрес
текст → адрес
адрес → текст
назад / вперёд / случайная страница
```

Новая работа — не «сделать библиотеку», а добавить к ней второй порядок:

```text
готовая полная библиотека
        +
исследование: можно ли расположить её страницы по смысловой стоимости
```

## Найденное состояние инфраструктуры

Публичный `all.bezrabotnyi.com` обслуживает текущий Babel-сервис.

`babel.bezrabotnyi.com` на момент проверки не является рабочим входом в библиотеку:

- HTTPS выдаёт сертификат, не соответствующий имени;
- HTTP возвращает `502`;
- nginx не содержит отдельного рабочего `server_name babel.bezrabotnyi.com`;
- найденный upstream `192.168.2.75:8098` ведёт на `Mobile Browser Login`, а не на Babel reader.

Поэтому восстановление канонического адреса — отдельная инфраструктурная задача, а не повод переписывать reader.

# Этап 0. Зафиксировать готовый фундамент

Цель: доказать, что существующая библиотека является базовым продуктом и не должна быть заменена новым декоративным экраном.

## Задачи

### 0.1. Технический аудит reader-а

Проверить существующий `library.html` и `library.js`:

- нулевой адрес;
- максимальный адрес;
- page64 ↔ decimal;
- `rank(unrank(n))`;
- `unrank(rank(text))`;
- переходы page64;
- random page;
- копирование адреса;
- мобильный layout.

### 0.2. Канонический API-контракт

Описать как текущую основу:

```text
raw rank:   нормализованный текст → число
raw unrank: число → 4096-символьная страница
```

Сохранить действующие URL и page64-адреса. Смысловой слой не должен ломать старые deep links.

### 0.3. Канонический продуктовый вход

Выбрать один основной reader:

- `babel.bezrabotnyi.com` — желаемый короткий адрес;
- `all.bezrabotnyi.com/library.html` — безопасный fallback;
- `all.bezrabotnyi.com` — объяснение проекта и вход в reader.

**Готово, когда:** пользователь открывает одну ссылку и сразу попадает в настоящую нумерованную библиотеку, а не в карту или login-экран.

**Параллельно:** 0.1 и 0.2 можно выполнять одновременно. 0.3 зависит от результата проверки nginx/upstream.

# Этап 1. Встроить смысл в существующий reader

Цель: не создавать новый «address-space explorer», а расширить готовую страницу библиотеки.

## Задачи

### 1.1. Русский первый экран reader-а

Сохранить reader и переписать подписи:

```text
Библиотека всех возможных страниц
Каждая страница имеет один адрес
Введите текст или номер страницы
```

Заменить английские кнопки:

```text
Find page       → Найти адрес
Open address    → Открыть адрес
Random          → Случайная страница
Current page    → Текущая страница
```

### 1.2. Панель «Смысловой эксперимент»

Добавить рядом с готовым raw-адресом, не вместо него:

- стоимость текста;
- среднюю стоимость на символ;
- поддерживаемую длину exact-расчёта;
- смысловой номер, если он доступен;
- понятное предупреждение о границе MVP.

Пример подписи:

> Обычный адрес уже точный для всей библиотеки. Ниже — эксперимент: насколько близко к началу окажется эта страница, если сортировать страницы по стоимости связности.

### 1.3. Две кнопки с разными обещаниями

```text
Найти обычный адрес
Проверить смысловую стоимость
```

Нельзя объединять их в одну кнопку «Rank», потому что это разные операции.

### 1.4. Ссылка из текста в reader

После поиска показывать:

- raw page64;
- полный десятичный адрес;
- кнопку копирования;
- URL, который открывает эту страницу в существующем reader-е.

### 1.5. Убрать Atlas из главного пути

Atlas оставить по отдельной ссылке:

```text
Литературный режим
```

Внутри него явно написать:

> Эти тексты помогают исследовать интерфейс чтения. Их координаты процедурные и не являются глобальной сортировкой всей библиотеки по смыслу.

**Параллельно:** 1.1, 1.2 и 1.5 можно делать одновременно после 0.2. 1.3 зависит от формулировок API. 1.4 зависит от существующего URL-контракта.

**Готово, когда:** пользователь сначала видит настоящую библиотеку, а смысловой эксперимент воспринимается как добавленный исследовательский слой.

# Этап 2. Доказуемый смысловой MVP

Цель: показывать смысловую сортировку только там, где она действительно посчитана точно.

## Задачи

### 2.1. Один короткий exact-режим

Выбрать один режим для публичного объяснения:

```text
страница длиной до 256 символов
energy → точный номер
равные energy → raw tie-break
```

Не показывать пользователю три конкурирующих режима `base256`, `cluster`, `hierarchical` без объяснения.

### 2.2. Прямая проверка round-trip

Для каждого semantic-примера проверять:

```text
text → semantic rank → semantic unrank → тот же текст
```

Отдельно проверять, что raw-адрес страницы остаётся тем же самым независимо от показа semantic-метрик.

### 2.3. Галерея реальных контрольных страниц

Сделать пять вызовов настоящего ranker-а:

1. связная русская фраза;
2. связная английская фраза;
3. та же фраза с опечаткой;
4. повтор одного символа;
5. случайный шум.

Показывать для каждой:

- текст;
- raw-адрес;
- стоимость;
- semantic rank, если длина поддерживается;
- статус «точно посчитано».

### 2.4. Русское объяснение стоимости

Текст рядом с числом:

> Стоимость — это сумма штрафов конечной модели за переходы между символами. Она не является человеческим мнением и не доказывает смысл сама по себе. Это вычислимая гипотеза о близости к языку.

### 2.5. Панель статуса

```text
Готово: полная нумерация всех страниц
Точно в MVP: смысловой порядок коротких страниц
Исследуется: один глобальный смысловой порядок для 4096 символов
```

**Параллельно:** 2.2, 2.3 и 2.4 можно выполнять одновременно. 2.1 и 2.5 задают общий контракт и должны быть согласованы до финального UI.

**Готово, когда:** ни один красивый пример не выдаётся за доказательство глобальной сортировки.

# Этап 3. Глобальный смысловой порядок — научная дорожка

Цель: решить единственную действительно новую задачу проекта: построить точный смысловой rank/unrank для полной 4096-символьной страницы.

Эта дорожка не блокирует использование готовой библиотеки и может идти параллельно с этапами 1–2.

## Задачи

### 3.1. Эталонный direct-DP

Для длин 8, 16, 32 и 64 построить медленный, очевидный счётчик energy buckets.

Он нужен не для production, а как oracle для проверки оптимизаций.

### 3.2. Состояние границы блока

Определить, что передаётся между блоками:

- состояние конечной модели;
- накопленная стоимость;
- число продолжений;
- точный формат таблицы перехода.

### 3.3. Chunked counting

Считать полную страницу блоками, сохраняя состояние на границах. Простое перемножение независимых блоков запрещено: оно теряет переходы между блоками.

### 3.4. Сверка оптимизации с oracle

Для каждой длины требовать:

```text
chunked_count == direct_count
```

### 3.5. Глобальный смысловой rank

После histogram по общей стоимости реализовать:

```text
номер = количество страниц с меньшей стоимостью
      + точное смещение внутри равной стоимости
```

### 3.6. Глобальный смысловой unrank

По номеру:

1. выбрать bucket стоимости;
2. выбрать путь по состояниям;
3. выбрать каждый следующий символ;
4. восстановить всю страницу.

### 3.7. Доказательства

Проверить:

- покрытие всего raw-пространства;
- отсутствие повторов;
- `rank(unrank(n)) = n`;
- `unrank(rank(page)) = page`;
- монотонность по стоимости;
- корректность переходов между блоками.

**Параллельно:** 3.1 и 3.2 стартуют одновременно; 3.3 зависит от обоих; 3.4 можно вести рядом с 3.3; 3.5 и 3.6 начинаются после устойчивого счётчика; 3.7 идёт с самого начала как набор admission-тестов.

**Готово, когда:** появляется единый точный смысловой порядок всей 4096-символьной библиотеки, а не блочная композиция и не выборка.

# Этап 4. Восстановить канонический адрес и production-маршрут

Цель: вернуть пользователю тот адрес, где уже была библиотека.

## Задачи

### 4.1. Найти настоящий старый deploy

Сверить:

- историю nginx;
- старые systemd-сервисы;
- DNS-записи;
- старые каталоги приложения;
- GitHub commit/deploy history.

Если отдельного старого репозитория нет, каноническим источником считать `site/library.html` в этом проекте.

### 4.2. Исправить `babel.bezrabotnyi.com`

Добавить отдельный nginx server block с правильным сертификатом и маршрутом в тот же Babel backend/reader.

Не направлять Babel-домен на `Mobile Browser Login`.

### 4.3. Сохранить fallback

Оставить рабочими:

- `all.bezrabotnyi.com`;
- `all.bezrabotnyi.com/library.html`;
- старые page64 deep links.

### 4.4. Production canary

Проверить на публичном домене:

- главную библиотеку;
- адрес `0`;
- random address;
- текст → raw address;
- next/previous;
- semantic MVP;
- отсутствие login-экрана;
- корректный сертификат.

**Параллельно:** 4.1 можно выполнять одновременно с этапами 1–3. 4.2 зависит от найденного старого маршрута и решения о каноническом backend-е. 4.3 и 4.4 идут после 4.2.

# Параллельная схема

```text
                ┌─ Этап 1: смысловой UI в готовом reader-е ─┐
Этап 0 ─────────┼─ Этап 2: короткий exact semantic MVP ──────┼─ Этап 5: выпуск
                └─ Этап 4.1: поиск старого deploy ──────────┘

Этап 3: глобальный 4096 semantic rank/unrank
  └─ отдельная научная дорожка, не блокирует Этапы 1–2
```

## Критический путь до понятного продукта

```text
аудит готовой библиотеки
  → русский reader
  → semantic-панель рядом с raw-адресом
  → пять реальных контрольных примеров
  → исправление канонического домена
  → публичный canary
```

## Что больше не является задачей

- заново строить reader;
- заново изобретать page64;
- делать hex-карту главным интерфейсом;
- генерировать литературные тексты, чтобы имитировать смысловой порядок;
- переписывать готовую raw-биекцию ради новой страницы.

Главный новый результат проекта — не ещё одна библиотека, а доказуемая перестройка порядка уже существующей библиотеки по смысловой стоимости.

# Подробный план: от нумерованной библиотеки к сортировке по смыслу

Статус: рабочий план текущего цикла.

## Главный результат

Собрать продукт, который сначала понятно показывает готовую библиотеку всех страниц, а затем поверх неё показывает исследование смыслового порядка.

Пользователь должен за одну минуту понять три факта:

1. Каждая возможная страница уже имеет ровно один номер.
2. По номеру можно открыть страницу, а по тексту можно найти её номер.
3. Отдельная научная задача проекта — перестроить тот же самый список так, чтобы связные страницы оказались ближе к нулю.

Это два разных слоя. Их нельзя смешивать в одном интерфейсе или описывать одним словом «адрес».

## Термины продукта

| Техническое слово | Русское название в интерфейсе | Смысл |
|---|---|---|
| raw address | обычный адрес | номер страницы в полном пространстве |
| rank | номер | позиция текста в выбранном порядке |
| unrank | открыть по номеру | восстановить страницу из номера |
| energy | стоимость связности | целое число, которое начисляет конечная модель |
| exact | точный расчёт | без выборки, генерации и округления |
| semantic order | смысловой порядок | сортировка по стоимости, затем по правилу разрешения равенств |
| student | конечная модель | таблица состояний, переходов и стоимостей |

Английские названия можно оставить в коде и API, но на главном экране пользователь должен видеть русские слова.

## Границы готового результата

### Уже готово и можно показывать как продукт

- Полная raw-биекция для страниц длиной 4096 символов над алфавитом из 256 знаков.
- Диапазон адресов `0 … 2^32768 − 1`.
- Операции «текст → адрес» и «адрес → текст».
- Точный смысловой порядок для страниц длиной до 256 символов.
- Обратимая 4096-символьная блочная композиция из 16 блоков по 256 символов.

### Не выдавать за готовое

- Глобальный смысловой порядок всех 4096 символов одной общей стоимостью.
- Доказательство, что литературные тексты Atlas занимают низкие позиции в общем пространстве.
- Сортировку случайной выборки вместо полного rank/unrank.

# Этап 0. Зафиксировать контракт и убрать двусмысленность

Цель: перед реализацией договориться, что именно мы называем готовым.

## Задачи

### 0.1. Контракт адреса

Зафиксировать:

- длина полной страницы: 4096 символов;
- алфавит: 256 знаков;
- raw-адрес: целое в `[0, 2^32768)`;
- передача больших чисел: десятичная строка и hex-строка;
- нормализация и padding пробелами;
- точное правило `rank(unrank(n)) = n`.

**Готово, когда:** один документ и один API-ответ описывают одинаковые правила.

### 0.2. Контракт смыслового порядка

Зафиксировать отдельно:

- стоимость страницы считается конечным student-ом;
- сначала сравнивается total energy;
- равные energy разрешаются точным raw-порядком;
- точность гарантируется только на поддерживаемой длине;
- для 4096 сейчас гарантируется обратимость блочной композиции, но не глобальный energy-order.

**Готово, когда:** в UI, README и API нет противоречивых формулировок.

### 0.3. Русский словарь интерфейса

Убрать с главного экрана слова `raw`, `rank`, `unrank`, `exact`, `semantic`, `Atlas`, если рядом нет русского объяснения.

**Можно параллельно:** с 0.1 и 0.2.

# Этап 1. Полная библиотека Вавилона — основной продуктовый контур

Цель: сделать понятный законченный продукт даже без смысловой сортировки.

## Задачи

### 1.1. Первый экран «Все страницы пронумерованы»

Показать только главное:

```text
Библиотека всех возможных страниц
0 … 2^32768 − 1
```

Две основные формы:

- «Открыть по номеру»;
- «Найти адрес текста».

Вторичный блок объясняет, что это полная нумерация, а не генератор.

### 1.2. Экран открытия по номеру

Поля и действия:

- десятичный/hex-адрес;
- кнопка «Открыть»;
- видимая страница;
- текущий адрес;
- «предыдущая» и «следующая» страницы;
- копирование ссылки.

Для страницы из пробелов нужен визуальный режим, где пробелы показываются точками только в отображении.

### 1.3. Поиск адреса текста

После ввода текста показывать:

- исходный текст;
- нормализованную страницу;
- полный raw-адрес;
- длину в символах;
- правило дополнения до 4096.

Здесь нельзя показывать «смысловой номер», если выбран raw-режим.

### 1.4. API и URL-контракт

Проверить и документировать:

- `POST /api/rank` для raw-адреса;
- `POST /api/unrank` для открытия страницы;
- deep link с адресом и длиной;
- ошибки слишком большого/отрицательного адреса;
- сохранение больших чисел как строк.

### 1.5. Тесты полной библиотеки

Минимальный набор:

- `0 → страница из padding-пробелов`;
- `1 → соседняя raw-страница`;
- максимальный адрес;
- случайные адреса;
- `unrank(rank(text))` совпадает с нормализованной страницей;
- переходы `next/previous` согласованы с `±1`.

**Параллельность этапа 1:** 1.2 и 1.3 можно делать параллельно после 1.1 и 0.1. 1.4 и 1.5 можно вести параллельно с UI, но финальный тест требует готового API-контракта.

**Этап завершён, когда:** новый пользователь без знания проекта открывает номер и находит адрес текста без чтения исследовательской документации.

# Этап 2. Лаборатория смысла — отдельный контур поверх библиотеки

Цель: показать научную идею на уже доказанном коротком пространстве.

## Задачи

### 2.1. Экран «Почему человеческое ближе к нулю»

Одна схема:

```text
страница
  → переходы конечной модели
  → стоимость
  → сколько страниц дешевле
  → смысловой номер
```

Каждый блок должен иметь раскрывающую подсказку на русском.

### 2.2. Показатель стоимости

Для введённого текста показывать:

- стоимость страницы;
- среднюю стоимость на символ;
- какие фрагменты дали наибольший штраф;
- предупреждение, что стоимость зависит от выбранной модели.

### 2.3. Точный короткий порядок

Для длины 256 показывать:

- смысловой номер;
- стоимость;
- правило разрешения одинаковой стоимости;
- кнопку «открыть по смысловому номеру»;
- round-trip результат.

### 2.4. Галерея контрольных страниц

Пять фиксированных классов:

1. связная русская фраза;
2. связная английская фраза;
3. фраза с опечаткой;
4. повтор одного символа;
5. случайный шум.

Для каждого образца показывать одинаковые поля: текст, стоимость, короткий номер, длину и режим точности.

Это должны быть реальные вызовы ranker-а, а не вручную расставленные красивые примеры.

### 2.5. Панель статуса доказательства

Три колонки:

- **Доказано:** полная raw-биекция;
- **Работает точно:** смысловой порядок до 256 символов;
- **Следующая задача:** глобальный смысловой порядок до 4096.

**Параллельность этапа 2:** 2.1, 2.2 и 2.4 можно делать параллельно после общего API-формата. 2.3 и 2.5 зависят от зафиксированного exact-контракта.

**Этап завершён, когда:** пользователь видит не «красивые страницы», а измеримое сравнение реальных страниц и понимает границу доказательства.

# Этап 3. Глобальный смысловой порядок 4096 — математический контур

Цель: получить настоящее `смысловой номер ↔ полная 4096-символьная страница`.

Это самый дорогой и рискованный этап. Его не нужно блокировать до запуска этапов 1 и 2.

## Задачи

### 3.1. Малый эталонный счётчик

Сделать медленный, очевидный direct-DP counter для длин 8, 16, 32 и 64.

Он нужен как эталон для всех оптимизированных реализаций.

**Готово, когда:** для малых длин можно перечислить energy buckets и независимо проверить rank/unrank.

### 3.2. Спецификация состояния блока

Зафиксировать, что передаётся между блоками:

- состояние finite student на границе;
- накопленная стоимость;
- число путей;
- точный формат transfer table.

### 3.3. Chunked counting

Разделить полную страницу на блоки, но считать не простым перемножением независимых количеств, а через состояние на границе блока.

Нужно доказать:

```text
chunked_count = direct_count
```

на малых длинах.

### 3.4. Полиномиальная/свёрточная оптимизация

Исследовать представление переходов как полиномов по energy и свёртку блоков. Это оптимизация, а не отдельная семантическая модель.

### 3.5. Глобальный rank

После получения histogram по total energy реализовать:

```text
rank(page) = count(energy < page.energy)
           + exact offset внутри равной energy
```

### 3.6. Глобальный unrank

Реализовать обратный выбор:

1. найти energy bucket по номеру;
2. выбрать состояние блока;
3. выбрать символ/переход на каждой позиции;
4. восстановить полную страницу.

### 3.7. Доказательства и тесты

Обязательные свойства:

- coverage;
- uniqueness;
- `rank(unrank(n)) = n`;
- `unrank(rank(page)) = page`;
- монотонность по energy;
- отсутствие потерь на границах блоков.

**Параллельность этапа 3:**

- 3.1 и 3.2 можно начинать одновременно;
- 3.3 зависит от 3.1 и 3.2;
- 3.4 можно исследовать параллельно с 3.3;
- 3.5 и 3.6 начинаются только после устойчивого 3.3;
- 3.7 идёт непрерывно начиная с 3.1, но финальная admission-проверка зависит от 3.6.

**Этап завершён, когда:** есть точный глобальный rank/unrank для 4096, а не только оценка, выборка или блочная подмена.

# Этап 5. Публикация и сопровождение

## Задачи

- обновить README и `notes/current/*` после каждого изменения контракта;
- запускать raw round-trip tests на каждый релиз;
- запускать semantic small-length tests отдельно от production smoke test;
- обновлять `graphify-out/` после изменений архитектуры;
- держать browser/cache/agent artifacts в `.gitignore`;
- deploy на `all.bezrabotnyi.com` только после локального и публичного canary;
- в релизном описании всегда разделять доказанное, MVP и открытый фронтир.

## Критерий выпуска

Выпуск считается успешным, если:

1. с чистого браузера открывается главная страница;
2. номер `0` открывает корректную нулевую страницу;
3. произвольный raw-адрес восстанавливает страницу;
4. введённый текст получает raw-адрес;
5. короткий semantic rank проходит round-trip;
6. английские термины не нужны для понимания основного сценария;
7. публичная страница не утверждает, что глобальная 4096 energy-сортировка уже завершена.

# Критический путь и параллельные дорожки

Минимальный путь до понятного продукта:

```text
Этап 0
  → 1.1
  → 1.2 + 1.3
  → 1.4 + 1.5
  → 4
  → 5
```

Независимая научная дорожка:

```text
3.1 + 3.2
  → 3.3
  → 3.5 + 3.6
  → 3.7
```

Параллельная демонстрационная дорожка:

```text
2.1 + 2.2 + 2.4
  → 2.3 + 2.5
```

Главное решение по приоритету: этапы 1, 2 и 4 дают пользователю понятный работающий продукт, даже если этап 3 потребует долгого исследования. Этап 3 нельзя имитировать декоративными текстами или картой.
